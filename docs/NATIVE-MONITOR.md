# 原生在线查询与游戏内控制适配

## 当前部署及定向消息核对（2026-11-05）

基础在线查询、公告/定时公告、踢人及封禁联动代码已经部署；相关开关由网页管理。下面各批“未部署”说明保留为历史，不能视为当前安装状态；部署不代表原生游戏效果已验证。

本轮只读复核固定镜像：`OnNoticeMessage` 转发给全部游戏进程，其游戏处理器调用 `GameWorld::send_all`；`OnBroadcastMsg` 对应游戏群体广播。`OnNoticeOtherChannelChatMsg` 依赖真实在线发送角色与接收角色，不能作为无发送角色的系统单发接口。没有把这些通道伪装成定向系统消息，没有发控制报文或注入进程。定向系统消息仍待找到并适配独立可靠通道，不用邮件功能替代本项。

## 只读查询范围

- 登录管理员在账号管理区点击“查询实时状态”，调用`GET /dnf-gm/api/v1/online/{uid}/live`。
- 返回数据库登录记录和原生 monitor 会话响应两个独立来源。字段来源和时间明确；登录表中的频道不是原生查询返回的实时频道。原生响应只说明账号是否在 monitor 会话表，不提供角色、会话唯一令牌、战斗状态、存档落盘证明或客户端存活证明。
- 响应为在线、离线或未知；未启用、指纹不符、快照过期、核心状态异常、繁忙、超时、报文不匹配都属于未知。**不会因为超时写登录表，也不能凭此解除装备修改所需的并发保护。**
- 网页只在点击时查询，无自动网络轮询。响应超过15秒或检测到本机时钟回拨后变为未知，保留原响应时间。切换账号或刷新时清除旧结果，迟到响应不覆盖新账号；错误紧邻查询按钮。

## 实现约束

原生接口是私网UDP，不是HTTP接口，也没有应用级认证。浏览器不能直接指定主机、端口、操作码或原始报文。服务仅查询现有账号；需要管理员会话，独立每会话12次/分钟、全局60次/分钟限流。

应用仅访问配置中**同一数据库私网IPv4地址**的固定monitor端口，不进行DNS解析，不接受公网、链路本地或云元数据地址。默认关闭`native_monitor_enabled`。原生单次查询最多750毫秒，仅一个并发socket，等待期间不持有MySQL连接；不自动重试。connected UDP限定回复源，校验固定长度、类型、目标UID、随机回显字、源地址/端口回填及状态取值。日志/HTTP返回不包含原始报文、网络地址和异常明文。

查询启用还要求新鲜采集快照、镜像指纹一致、核心状态正常，以及当前monitor程序SHA-256与本次适配指纹一致。监控只读固定镜像文件路径，缓存由路径、设备、inode、大小、mtime和ctime组成；文件变化时有界重新计算哈希，拒绝空文件、符号链接、非普通文件或超过15MiB的程序文件。文件缺失/不兼容只禁用该功能，不将其计入核心故障从而停止GM。

这一校验是版本匹配，不是网络对端的密码学身份认证；受信私网或宿主机遭入侵时不能保证回复真实。

## 已取得的实际证据

2026-11-05（Asia/Shanghai）对现有服务器进行了只读探测：

1. 原生manager和monitor均存在TCP/UDP监听，不将容器内缺少`ss/nm`工具导致的空输出解释为“没有接口”。通过宿主机网络命名空间核实了监听归属。
2. 读取现有二进制的符号和限定函数反汇编，不附加调试器、不注入运行中进程、不修改程序。manager存在`OnWebNoticeBroadcast`，monitor存在`OnWebQueryUserState`、`OnWebNoticeSingle`、`OnUserRepel`。
3. 已核对固定的19字节账号状态查询和接收/返回路径。一次非玩家探针返回离线；随后从宿主机私网地址对两个现有账号各发送一次只读查询，收到有效离线响应，回显和来源字段均匹配。探测时没有在线玩家可用于正向在线验证；本地合成UDP测试覆盖在线返回，不替代真实在线样本。
4. 游戏进程中的`Inter_WebNoticeSingle::dispatch_sig`最终调用全世界广播；`Inter_UserRepel::dispatch_sig`调用断线处理。因此原生公告和踢人有真实处理链路线索，不必先假设只能新增Frida桥接。
5. `OnWebNoticeSingle`的“Single”不是给单个玩家发私信：monitor会转发给其游戏服务器，再由游戏全体广播。不得把它包装成私信API。
6. 本轮未发送公告、私信、踢人、封禁或物品变更报文，未修改游戏表，未重启DNF、mihomo、cliproxyapi、Docker或Nginx。原始二进制、反汇编、玩家UID、网络配置和SSH凭据仅保留在私有工作区，未纳入开源仓库。

## 写控制的不变边界

- 公告/踢人处理链路没有本次已经验证的业务成功回执；UDP发送完成不能证明游戏效果。需要单独区分“准备、已尝试发送、服务接收证据、效果未知/已验证”，不能复用充值的“同事务已完成”含义。
- 操作意图及目标先持久审计；发送前占用唯一执行权，发送或最终审计阶段响应丢失后不能自动重发。DB事务不能与游戏网络效果一起原子提交。
- 公告明确发送范围、编码和实际报文长度；私信须继续核对独立寻址处理链路，不能复用广播冒充私信。
- 踢人确认目标账号/角色归属；在线核对不能提供会话唯一令牌，不能承诺精准踢出某个历史连接。封禁与踢人是两个不同步骤，分别记录结果和部分成功。
- 定时公告、定时奖励需持久调度与执行去重；不能依赖浏览器计时器。
- 不增加任意命令/原始报文入口，不发布原生管理端口，不新增Frida、运行时注入或更换游戏镜像。

## 安装与回滚

1. 随版本包升级应用和`deploy/monitor.py`，只重启GM自身及其监控，不动核心服务。其他已开发功能所需的004/005/006迁移仍按部署文档完成；本批没有新数据库迁移或权限。
2. 先保持`native_monitor_enabled=false`。检查监控快照具有`native_monitor_sha256`并符合适配版本；应用使用的Docker私网IPv4须已经在GM单元的`IPAddressAllow`中。不要扩大为整个公网或发布端口。
3. 显式配置`native_monitor_enabled=true`后重启GM，在应用实际systemd沙箱内验收查询、未知/超时、页面与资源预算。本轮宿主机探针不是这一沙箱验收的替代。
4. 禁用时设回false；旧版本不认识此配置键，回滚至旧版本前移除新增键或恢复旧版兼容的私有配置。不要删除审计和诊断历史。

合成浏览器测试：先本地构建并在回环地址提供`web/dist`，运行`tools/browser-native-session.mjs`；可设置`PLAYWRIGHT_MODULE`、`CHROME_EXECUTABLE`、`DNF_GM_BROWSER_OUTPUT`。测试只拦截合成API响应，不对真实账号或游戏服务操作。


## 原生控制发送层（第九批历史基础，第十批已接入网页）

新增内部 `NativeControlTransport`，只允许固定类型的全服公告和账号踢人，不接受公网目标、操作码、原始报文或角色选择字段。公告使用固定266字节报文，UTF-8文本最多254字节并保留终止零；拒绝空白和控制字符。这是协议缓冲区限制，不涉及道具数量规则。UTF-8内容的游戏客户端显示仍未验证。

- `native_control_actions` 默认空；还要求各动作的明确激活记录、已启用原生只读适配、匹配的镜像与monitor指纹、新鲜正常快照。
- 与查询共享一个并发槽，750ms超时，不等待虚构的业务回执，不自动重发。
- 测试账号限制生效时不允许广播；踢人只能命中测试目标。不会把广播伪装成单人私信。
- 返回 `transport_status=not_sent/sent/uncertain`，始终 `effect_status=unknown`。进入发送调用后的异常或短写属于不确定，连接前失败属于未发送；关闭socket失败不推翻已经完成的发送。
- 发送层本身不做数据库写入。**第十批编排先原子提交防重占位和审计，再发送一次，最后单独记录传输结果。** 防重提交断线不允许发送，结果保存失败不允许自动再发。网络效果不能与MySQL事务宣称原子提交。

配置样例保留空动作列表；尚未在生产启用这些动作。第九批仅实现发送层，不构成完整控制功能；第十批的编排和网页见下文，需要007迁移。回滚到不认识 `native_control_actions` 的版本时，恢复兼容私有配置或移除此新增键。

### 私信后续适配证据（未启用）

本轮只读检查 `OnNoticeOtherChannelChatMsg`：当前研究的非空消息路径先按发送方角色编号查原生会话，再查接收方角色；发送方缺失会直接结束，接收方缺失另行反馈。它还检查黑名单及已注册GM标记。`OnGMRequestMid` 涉及在线账号、角色名查询与转发，不能仅因名称包含GM就视为独立系统私信入口。

因此，下一步需要继续查证原生GM会话/系统消息路径或明确的管理员发送角色机制，不能填一个不存在的发送编号就宣称私信可用，也不能借用普通玩家身份。这里只记录已观察路径，不断言其他路径不存在。限定反汇编证据留在本机私有研究目录，不进入公开仓库；本轮没有发送这些候选报文。


## 第十批：公告、踢人与封禁联动的完整管理流程（本地）

### API与界面

统一前缀 `/dnf-gm/api/v1`：

- `POST /native-controls/preview`：5分钟、会话绑定预览。动作 `native-notice`、`native-kick`、`native-ban-kick`。公告无UID，后两者必须选择账号；原因必填。
- `POST /native-controls/{operation_id}/confirm`：CSRF、Origin、5分钟内密码重新认证、会话匹配、幂等键校验和限流。
- `GET /native-controls/{operation_id}`、`GET /native-controls?uid=...&page=...`：只读结果与每页50条历史，支持按账号检索。历史从007专用索引表读取，不在所有业务操作JSON中扫描UID。
- `POST /native-controls/{operation_id}/cancel-preview`：行锁核对后取消未发送预览；当前单管理员重新认证后可以取消旧会话预览，不能取消已占位操作。确认仍严格绑定原会话。
- 通用 `/operations/{id}/confirm` 拒绝原生动作；通用查询/玩家历史能够显示原生状态，不将其写成充值“数据库已提交”或“仅预览”。

“游戏内控制”页面提供公告内容、UTF-8字节计数、就近必填错误、明确的全服确认框、选中账号快捷入口、控制历史与原编号查询。确认前冻结目标，不随当前账号切换而改变。刷新后只恢复查询，不自动确认；不确定时每5秒只读查询原编号，隐藏页面停止。离开不确定结果需明确确认，原记录继续留在数据库历史。

### 发送一致性与审计

1. 在同一MySQL连接锁定操作，核验会话、幂等键、过期时间、目标、预览指纹、程序/镜像、新鲜核心状态、资源阈值和事务表。
2. 同事务写入唯一幂等键、`dispatching`占位及审计。封禁联动同时写入本后台处罚标记；不覆盖其他来源处罚，已有有效处罚要求使用独立踢人。
3. **仅在占位事务明确提交、连接释放后**调用发送层一次。占位提交断线时不发送；进程退出、响应丢失或重复确认均不能重新发送已占位操作。
4. 发送前再次核验启用/资源条件。发送结果与阶段审计在第二个事务记录。结果保存失败保留原占位为待确认；不通过任务重试或重新启动来重放。
5. 封禁的数据库结果与踢人的传输结果分别保存。封禁已提交、踢人未发送/不确定是合法的部分结果；不会因为踢人失败撤销封禁。普通解封接口兼容该处罚所有权。

状态：`preview`（未发送）、`dispatching`（已占位，结果待确认）、`sent`（指令已发送）、`not_sent`（未发送）、`uncertain`（无法确认发送结果）、`cancelled`（取消预览）。所有原生网络效果仍为unknown；不承诺立即踢出特定登录会话，因为当前原生查询没有唯一会话令牌。

### 安装与激活

- 新增007管理库迁移和 `native_controls` 表的SELECT/INSERT权限，运行账号没有索引表UPDATE/DELETE权限。安装使用更新后的provision；已有环境使用 `deploy/upgrade-native-controls.py`，不得重复provision。脚本不启用能力、不重启核心服务、不发送游戏指令。健康检查要求007；仍须保留所有前置迁移。
- 默认 `native_control_actions: []`。显式添加 `native-notice` / `native-kick` 时，还需各自的 `write_approvals` 为true和已启用的原生monitor查询。封禁联动另需原有 `ban` 激活；不要把 `native-ban-kick` 写入发送层动作配置。
- 测试UID限制未解除时禁止全服公告；踢人仅限测试账号。不为测试广播而偷偷解除全部写入的测试范围。
- 上线前验证GM实际systemd网络沙箱、程序适配、资源与服务状态；本轮合成接口和本地回环测试不替代生产控制效果。
- 回滚保留007表、处罚、审计及原操作编号。不会撤销已发送公告、已提交封禁或其他游戏效果；旧版本不认识新配置键时恢复兼容配置。不要把dispatching改回preview，也不要通过整库恢复撤销一次控制。


## 第十一批：定时公告

本地定时运营复用本模块的原生公告预览与防重确认，不增加其他报文。计划期次和操作预览在同一事务建立，明确提交后释放连接再发送；重启恢复只核对或取消尚未发送预览，不重发占位指令。需要008及默认关闭的定时执行器，不改变原生动作启用条件。详见[定时运营](SCHEDULES.md)。生产未部署，游戏效果仍未核验。

## 2026-11-05 定向消息补充核对

继续检查已有原生静态文件，未发送任何候选报文：

- `OnWebNoticeSingle` 虽含Single，实际调用 `SendAllToGameServer`，游戏处理也没有按目标玩家投递；不能作为私信接口。
- `OnServerMessageInfo` 同样向全部游戏组件转发；对应 `Inter_NoticeServerMessageInfo` 更新共享服务器消息后调用 `send_all_with_state`，不是指定UID消息。
- `Inter_BroadcastMsg` 调用 `send_group`，当前分组条件并非指定玩家；也不替代系统私信。
- 已检查的跨频道聊天仍需要真实发送会话；未借用玩家身份、注册虚假GM会话或注入运行时代码。

这些证据排除了上述候选，并不证明镜像不存在其他通道。指定玩家系统消息继续标记未适配；下一步须有可核验的独立定向入口，或明确的专用管理员发送会话方案，不能仅通过网页开关伪装成支持。
