# 第三十四批：监控握手、完整出站执行与网页结束维护

2026-11-05。本批为本地开发与隔离验证，**没有连接生产，没有部署或执行真实游戏组件的停止/恢复**。原十组及补充功能、唯一管理员网页权限、真实图片素材、最终UI与生产发布范围不变。

## 本批接通的路径

`网页维护确认 → 管理库请求/审计 → 固定出站包 → ExecutionWorker → 原数据库排空 → 游戏与其余写入者退出 → MaintenanceSession.open`

`网页明确结束维护 → 同事务子请求/父链接/审计 → 原编号close出站包 → MaintenanceSession.close_restore → 关窗/原数据库核对/按原状态恢复/健康检查/解冻`

这条路径已通过真实隔离MySQL5.7、真实文件锁与持久日志、**合成60项s6服务**的端到端API测试。未把合成服务、数据库提交或进程退出等同于生产游戏效果。

### 已安装监控握手

- 校验固定发布目录源码、监控配置、完整维护策略及实际加载模块路径；拒绝可写文件、目录、链接和发布切换。
- 将监控进程PID、启动时刻、boot ID、systemd MainPID、固定脚本命令行、双时钟新鲜度绑定到原配置与源码。
- 新维护要求普通游戏/网关健康、资源门槛与全部受保护服务正常。数据库排空之后、首条游戏命令之前再次核验。
- 恢复路径的身份检查仍校验来源、进程、版本、资源和受保护服务，但不把已过期的装备写许可重新变为有效；原会话另行核对停止组件与绑定。
- 监控握手证据只供固定root流程使用；网页概览不返回发布路径、boot/PID绑定及配置哈希。未通过握手时网页显示“暂未通过核验”，不误报“未安装”，不回显私有错误路径。
- 修复监控systemd单元缺少`src`导入路径，并禁止生成运行时字节码。

### 完整执行器与心跳

- 完整工作器要求原协调器、全组件生命周期与数据库排空适配器，不接受game-only适配冒充完整维护。
- 维护与恢复耗时阶段每5秒只读发布状态；心跳不申请数据库连接、不探测或修改游戏进程。结束前停止并等待心跳线程退出。
- 重复确认、重复结束请求只查询原记录。游戏退出后、窗口签发前中断的申请不会自动重放退出或重新签窗口。
- 此处是完整执行**库路径**；生产CLI、固定systemd安装和异常恢复联动尚待交付，不能仅凭文件存在宣称执行器已安装。

### 网页结束维护

- 新接口：`POST /dnf-gm/api/v1/maintenance/requests/{op}/close`，独立的严格确认字段`acknowledge_restore`、原计划指纹及幂等键。
- 使用由原申请确定的子操作号、全局唯一幂等键；子请求、父申请链接与“结束维护已排队”审计在同一MySQL事务提交，不提前记为恢复成功。
- 每次投递复核原子请求与审计的绑定。已进入恢复/已完成时只返回原结果，不重发服务命令。
- 新维护开关关闭后仍能结束原维护；唯一管理员可重新登录后执行恢复，不受原预览会话过期限制。仍需当前会话、CSRF/Origin及近期密码认证。
- 只允许有新鲜执行器状态、原计划匹配的已开启窗口申请结束。异常或未知阶段没有伪造的“强制成功”入口。
- 浏览器在POST前保存结束维护幂等键；超时、刷新只查询原编号。明确未保存的请求可由用户用同一键再确认，已保存未投递的请求只补投递原包。
- 独立确认框说明关窗、原服务恢复、已完成修改不回滚；缺少勾选或浏览器存储失败在确认框内提示。手机端验证无横向溢出。
- 新申请清除上一轮结束维护键，防止跨维护意外复用。历史、排队、恢复中与已结束分别显示。
