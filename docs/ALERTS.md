# 独立主动健康告警

状态：本地实现与隔离测试，尚未在生产启用。第十八批另接入可选管理库备份/恢复证据告警（见`BACKUP-HEALTH.md`）；任务失败告警与自动修复不在当前实现内。

## 覆盖与边界

- 独立 `dnf-gm-alert.timer` 每次上一个任务结束30秒后检查一次，不依赖GM进程存活。
- 检查采集文件缺失/过期/未知、GM `/health` 接口、当前核心状态、可用内存、Swap和磁盘余量。核心状态来自已有固定采集器，不重复执行Docker或systemctl检查。
- 同一个规则需要两次不同观测、至少间隔15秒才确认异常或恢复。重复的采集时间戳不算新观测；超过90秒的检查间断重新确认。未知数据不会清除已经发生的故障。
- 仅当前有效、已验证的维护窗口会把游戏核心项标为未知，避免预期停游戏引起虚假恢复；资源及GM接口仍正常检查。
- 每个规则仅保留一个待通知的最新变化，完整变化历史保留最近100条。通知停用时仍记录历史；停用期间的故障已经恢复后，不补发过时故障。
- HTTP 2xx仅记为“接收端已接受”，不是人已阅读。断线/超时后使用同一事件ID退避重试；接收端应按ID去重，不能承诺恰好一次通知。
- 不含玩家账号、物品、密码、Host地址、Webhook URL、token或异常正文。网页接口仅返回白名单字段，过期报告显示历史状态，读取失败清除旧状态。
- 没有新增数据库连接池；健康请求使用GM已有的最多3连接池。无游戏表权限、Shell/SQL入口、服务重启能力或网页配置通知地址的接口。

## 部署（维护者操作，默认关闭）

1. 随版本发布源代码与前端。普通安装不会主动启用通知。
2. 将 `deploy/alerts.example.json` 安装为 **`/etc/dnf-gm-alerts.json`**。此文件故意不放在现有750的`/etc/dnf-gm/`目录，避免给观察器开放数据库凭据所在目录。
3. `health_host` 必须与GM允许的Origin主机匹配（只填`host[:port]`，无路径/协议），与现有安装脚本健康检查的Host一致。访问地址固定为服务器回环`127.0.0.1:8765`。
4. 阈值单位：`memory`、`swap`是MiB；`disk`是GiB。默认256/1536/2，阈值仅影响通知，不修改已有保护阈值。
5. `webhook_url`为空时仅保留本地历史。启用时使用维护者明确选择的HTTPS443接收端，可配置`webhook_token`作为Bearer头。通用JSON协议不是任意消息平台的原生机器人格式，需要接收端适配。
6. 运行 `sudo /opt/dnf-gm/current/deploy/enable-alerts.sh`。脚本创建独立无登录系统用户`dnfgm-alert`，配置文件root所有、该用户组只读640；只启用自身定时器，不重启GM、DNF、mihomo、cliproxyapi或Docker。
7. 用`systemctl status dnf-gm-alert.timer dnf-gm-alert.service`检查实际运行；在GM“运维诊断→主动健康告警”核对新时间和各项状态。启用后首次正常状态不会发送“恢复”通知。

接收端请求体示例（合成数据）：

```json
{"source":"dnf-gm","schema":1,"events":[{"id":"aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa","key":"gm","state":"firing","occurred_at":1793830000,"label":"GM接口不可用"}]}
```

网络不使用环境代理，不跟随重定向，不关闭TLS证书校验。单请求3秒socket超时，整个oneshot由systemd限制15秒，包括DNS/慢响应。接收端DNS是维护者的信任选择，浏览器无法输入地址。不要把敏感数据库数据加入通知。

## 状态与恢复

- `/var/lib/dnf-gm/alerts/private.json`：600，持久防重和退避状态，仅观察器可读写。
- `/var/lib/dnf-gm/alerts/public.json`：644，脱敏报告；GM只读。
- `/var/lib/dnf-gm/alerts/worker.lock`：避免两个执行器重叠发送。
- 原子写入并同步目录；发送前先保存意向，发送后保存接受结果。若最终保存失败，下次仍可能重发相同事件ID。
- 私有文件损坏或在已有公开报告时丢失，观察器直接报失败，不静默初始化并重复发送。维护者需核对并恢复同批状态；不要把删除状态当作普通故障修复。
- 时钟倒退时保留原状态并失败；核对系统时间后恢复。网页按请求当前时间重新判定报告有效期。
- 失败日志只写固定事件，不包含异常文本和接收端响应。

## 资源与限制

观察器加入原有`dnf-gm.slice`，仍共享 **192MiB / 单核25%**，自身上限32MiB，无常驻线程和新数据库连接池。无提升现有资源预算。

“独立”仅指不依赖GM网页进程；整台服务器断网、整个slice受资源压力、定时器停用或观察器自身故障时，本机通知仍可能失效。网页会把超过90秒的报告标为过期，但这不替代外部可用性监控。生产资源成本与真实通知接收仍待验证。

## 升级与回滚

更新源代码后，维护者重新运行`enable-alerts.sh`更新单元定义；不修改私有配置和历史。回滚到不包含告警代码的旧版本前，仅停止并禁用`dnf-gm-alert.timer`，等待/停止自身oneshot，保留状态与配置。旧版若不识别`alert_file`配置键，移除该键；不要删除审计或其他管理库。

## 本地验收

单元/集成测试覆盖持续故障去重、恢复、未知/旧观测、时钟、重启、失败退避、响应丢失、状态损坏、排他执行、文件权限、白名单脱敏、鉴权、限流和禁止网页写入。浏览器夹具验证桌面/390px手机、近处错误、过期不冒充正常、只读请求。没有向真实接收端发送通知，也没有触发生产故障。

## 可选备份证据规则（第十八批）

`backup_health_enabled`默认false。启用后观察器只读`/var/lib/dnf-gm/backup-health.json`，新增管理库备份与当前备份恢复核验两项规则；无额外数据库连接，不在观察器中进行大文件哈希。备份文件核对由维护工具完成；证据过期/失败会告警，其他备份的恢复记录不冒充当前备份通过。新观察器可读取旧六规则状态并添加两项。若回滚到旧观察器，需先停用自身定时器并保留新版状态，不能把不识别的新规则清空后宣称通知无缝回滚。
