# 受控旧 GM 发布包清理（开发版）

> **当前权限方案（2026-11-05，012迁移）**：最终安装对唯一管理员初始化全部已实现能力、开放全部账号，之后在“功能与版本”网页启停；下文早期 `writes`、`write_approvals`、测试UID或执行器文件开关仅作历史/适配说明，不是新版日常启用步骤。数据库列权限和原生/维护适配由部署者安装完成，不要求管理员每次SSH授权；权限开放不替代真实协议实现。见[网页权限手册](CAPABILITIES.md)。本地开发尚未代表生产已升级。

此功能清理**明确选择的旧 GM 应用产物**，不是服务器文件管理器。默认关闭；普通安装不会自动激活。目前仅在本地隔离目录、MySQL 5.7 和合成浏览器中验证，尚未生产部署。

## 操作与结果

1. 运维诊断 → 受控旧 GM 产物清理 → 刷新签名清单。
2. 选择 1–5 个明确版本，填写原因，生成预览。名称、条目数、分配空间估算固定于预览；预览最长 5 分钟，且不超过源票据有效期。
3. 输入“删除旧GM产物”，必要时重新输入管理员密码，然后确认一次。
4. 保存操作编号，查询同一编号。后台先把 `queued` 与审计在 MySQL 同一事务保存，再投递请求；**入队不等于删除成功**。
5. 执行端结果为 `completed`、`rejected` 或 `needs_review`。后者可能包含已删除的目录和部分完成的目录，不提供自动重放。

文件系统删除与 MySQL 不可能合为一个事务，多目录也不具备原子回滚。目录分配块数是估算，不保证磁盘立即释放相同容量。业务审计保留入队事实；root 执行收据保留逐目录事实。查询接口同时展示两者，不把入队审计改写成已删除。

## 精确范围与保护

- 唯一删除根是 `/opt/dnf-gm/releases`，网页不能提交绝对路径、命令或 SQL。
- `current`、`previous` 及**目录修改时间最新的两个版本**受保护。目录修改时间只是额外保留策略，不代表准确部署时间。
- 包必须有 `SOURCE_REVISION`、`SHA256SUMS` 和 `pyproject.toml`，目录树属于 root、不可被组或其他用户修改。标记只是包识别，不证明内容可信或签名过源码。
- 拒绝符号链接、特殊文件、普通文件硬链接、子挂载点、跨设备、超深目录和过大目录树；根目录或指针异常时整个清单不可用。最多 100 个目录条目、每包 20,000 个树条目、48 层、8 秒扫描预算，清单生成另有约 15 秒轮次预算。
- 扫描票据绑定目录名、设备、inode 和元数据指纹（路径、类型、大小、mtime、ctime），由 root 私有密钥 HMAC 签名。不是文件内容签名；可信 root 维护操作仍须遵守维护锁。
- 安装、回滚和执行清理共用 `/var/lib/dnf-gm/maintenance.lock`；不要删除重建锁文件。确认后执行端重新核验整个选择，删除前再检查指针保护及目录身份；使用 Python 支持抗符号链接攻击的目录 fd 删除实现。
- 不触及 DNF 数据、数据库、备份、日志、私有索引、素材、GM 审计、执行收据或当前/回滚版本。不会重启游戏、mihomo、cliproxyapi、Docker。

如果历史包由 `dnfgm` 拥有、含链接或不符合打包格式，显示不可清理。不要为了让按钮变绿而递归修改整个 `/opt` 的权限或删除任意目录；维护人员应先核实该包的实际归属。

## 显式安装与启用

先按 `DEPLOYMENT.md` 发布带此功能的版本，确认回环健康及新页面只读功能。然后由维护人员检查当前/回滚路径、权限与恢复记录，再执行：

```bash
sudo bash /opt/dnf-gm/current/deploy/enable-release-cleanup.sh
```

该脚本只安装专用 worker/timer、目录及应用的 inbox 写权限 drop-in，不编辑私有配置，也不重启应用。单独把 `/etc/dnf-gm/config.json` 的 `cleanup_enabled` 设为 `true`，保留文件原权限和其他字段，最后在已审查的 GM 部署窗口**仅重启 GM 应用**使设置/drop-in 生效。不把凭据贴到命令记录或文档。

默认路径无需配置：

| 路径 | 所有者/权限与用途 |
| --- | --- |
| `/run/dnf-gm/cleanup.json` | root 写、应用只读的签名清单；网页不返回票据 |
| `/var/lib/dnf-gm/cleanup/private/key` | root 0600；签名密钥，禁止公开 |
| `/var/lib/dnf-gm/cleanup/inbox` | root:dnfgm 0770；应用仅能新增/核对请求，文件0600 |
| `/var/lib/dnf-gm/cleanup/results` | root 写、应用只读；不可变终态及中断核对收据 |
| `/var/lib/dnf-gm/maintenance.lock` | root 维护互斥锁；应用无写权限 |

应用配置支持绝对路径主要用于隔离测试；生产执行器使用上述固定路径。不能仅修改应用路径就宣称执行器已切换，路径不一致应报不可用而不是自动放宽权限。

worker 是单独的 root oneshot，不连 MySQL、不执行 shell、不持有服务控制接口、不访问网络。与应用及监控共用原 `dnf-gm.slice` 的 192 MiB / 单核25%预算。每轮至多处理一个任务，30秒后再运行；执行前检查实时可用内存≥256MiB、Swap剩余≥1536MiB以及45秒内核心检查通过。原监控和保护机制不变。扫描清单不等于获准删除。

普通升级会在维护锁内暂停原来已运行的清理 timer，仅在升级健康通过后恢复它；原来没启用的不会自动启用。失败时保持暂停，维护人员核对后再恢复。回滚脚本**禁用清理 timer（含下次开机）**，旧版不认识新配置键时还须恢复兼容配置；业务库、审计和收据不删除。

## 断线、中断与人工处置

- **确认响应丢失**：浏览器只读查询原编号，不创建第二个任务。若查询仍为 `preview`，并不证明此前请求不会稍后提交；使用“锁定核对并取消未入队预览”。服务端持有同一操作行锁：若已入队拒绝取消，若尚未入队则持久取消并留审计，之后原确认不能提交。
- **已入队但没有请求文件**：管理员显式“仅重新投递原任务”，只写同一个操作编号和已冻结的票据，不重新授权、不自动延期；票据过期由执行器拒绝。
- **worker 中断**：下轮先核对旧收据，即使资源不足也把 `executing` 标记为 `needs_review`，不再次执行删除。保留旧编号核实目录；不要删除收据让同一个编号重新执行。
- **收据损坏、权限错误或请求摘要不匹配**：页面显示结果不可核对，禁止重新投递；维护人员恢复/核查 root 收据，不以重新创建任务解决未知结果。
- **inbox 满或崩溃临时文件**：应用最多允许32个队列条目，执行器每轮最多查看100个。不会自动删除不认识的文件。维护人员在维护锁下检查 `.tmp` 文件和原操作记录；确认没有活动写入、没有未知提交后才处理残留临时文件，保留已投递请求及所有收据。
- **停用**：先将私有配置 `cleanup_enabled=false`，仅重启GM应用；维护人员停用 timer 后还需核对已运行 worker 是否结束和所有已入队编号。停 timer 不会撤销已确认的任务，不能把它当回滚。

安全测试只在临时目录模拟删除。生产验收应先验证不可选保护项、权限与只读清单，再由维护人员选中确实可丢弃的合成 GM 测试包走一遍结果核对；不能为验收随意删除旧生产发布包。
