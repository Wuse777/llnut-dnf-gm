# 任务检索、存档排查与单槽修复

入口：**账号与角色 → 查看详情 → 任务检索与修复**。查询对全部账号开放，不需要维护窗口。页面下方「单任务槽清理」使用独立写能力 `quest-clear`，所有者可在网页「功能与版本」直接启停；本次部署默认开启、全部账号范围。执行写入前需在网页维护中心显式开启维护窗口，页面不会自动停止游戏。

## 可以查看什么

- 当前镜像 `taiwan_cain.new_charac_quest` 的20个进行中任务槽、任务编号、原始进度值及紧急任务编号。
- 完成标记分页，每页50项；按任务编号核对是否在进行中、是否有完成标记及匹配PVF中的定义。
- 完整PVF索引按名称字面子串或编号搜索，每页20项；按编号核对展示前置任务名称、完成标记及进行中槽，不把多前置关系擅自解释成AND/OR或可接资格。
- 任务名称、分类、等级范围、前置条件原值和条件说明；进行中列表可按名称/编号筛选、仅显示疑点。
- 重复任务槽、空槽残留进度、编号超出原生范围、匹配索引缺少任务定义、进行中同时有完成标记等**线索**。重复/循环任务可能同时带完成标记，不直接判定损坏。

在线任务进度可能尚未落库，页面显示采集时间并说明只读的是数据库快照。进度字段可能同时编码多个条件，不能显示成百分比。未完成不等于可接，前置条件没有被解释成简单AND或自动通过。没有存档、格式异常、未知版本与完成数为0明确分开。

## 固定格式依据

只读核对当前原生 `DB_LoadQuest::GetUserQuest`、`UserQuest::set_quest`、`WongWork::CQuestClear::isClearedQuest` 和 `uncompress_zip`：

- 原生加载/保存表为 `new_charac_quest`，不是旧 `charac_quest` 的任务分段字段。
- 完成存档使用4字节长度头和zlib，原生长度取低30位；当前数组为30000字节，合法完成编号1至29999，编号0保留。每个编号对应一个字节，不是每字节8任务的位图。
- 非零按原生逻辑显示为有完成标记；非0/1或保留位值额外提示，不修改原值。
- 未适配程序指纹只显示槽位、不解码完成数组。已适配程序SHA-256为 `8859c99d8290dc5fb58151444138cf2697b2bfff12d47d6159596a03f20b5261`。
- 空或不完整压缩存档不擅自补零；解压上限固定，不接受尾部数据。

程序与反汇编保存在本机私有研究目录，不进入Git。真实客户端任务窗口未参与验证。

## 离线索引与安装

在维护电脑上运行（不在云端解析完整PVF）：

```bash
PYTHONPATH=src python tools/enrich_catalog_quests.py old-catalog.sqlite Script.pvf new-catalog.sqlite
```

工具校验PVF与旧索引指纹，读取 `n_quest/quest.lst` 和任务定义，产生**新索引副本**，保留原有物品、职业、宠物等索引数据及权限字段。已有目标文件拒绝覆盖。当前匹配PVF提取3017项。

将新索引原子替换为已配置的只读索引，旧文件保留私有备份。运行用户只增加 `new_charac_quest` 必要列的SELECT；原只读授权不包含UPDATE；本次新增单槽清理专用授权见下文，不修改游戏表结构，不增加管理库迁移。安装与版本升级已同步此授权。

索引缺失或PVF不匹配时仍可看存档编号，但不提供可能错配的任务名称，也不把缺少索引视为任务不存在。实时PVF快照过期会提示当前名称匹配仅依据配置。

API：`GET /dnf-gm/api/v1/characters/{charac_no}/quests?page=1&quest_id=0`，按角色主键读取；只返回20槽与当前50条完成记录，无无界游戏全表扫描。错误不会触发自动写入修复。搜索API为 `GET /dnf-gm/api/v1/characters/{charac_no}/quests/search?q=名称或编号&page=1`。

## 单任务槽清理

- 在进行中卡片点击「选择此槽进行清理」，或在下方选择一个任务槽；填写原因、生成预览，再确认。支持清理编号为0但仍有残留进度的槽。
- **只清零所选槽的 `play_N` 和 `play_N_trigger`**。保留其他19槽、完成标记压缩数据、紧急任务编号及 `quest_notify` 通知存档。
- 不完成任务、不发奖励、不补发或回收任务道具、不保证清理后立即可重接。不是游戏原生放弃流程或在线热更新。结束维护后由游戏重新加载。
- 明确显示所选任务名称/编号、槽号、原始进度前后值、账号与角色及原因；未识别或PVF不匹配的名称不伪装成已识别。
- 引用绑定角色归属、程序/镜像/PVF版本、全部任务槽以及两个原始BLOB的SHA-256；预览或确认期间任务变化要求重新读取。
- 沿用维护窗口、持久执行意向、幂等编号、同事务条件更新/不可变快照/成功审计。响应丢失只查询原编号，禁止自动重发。
- 快照为 `qf1031-quest-slots-1`：全部槽和未改动BLOB的摘要；**不是完整游戏库备份或61字节物品存档**，没有通用任务恢复入口。
- `GRANT UPDATE` 仅覆盖40个固定的任务编号/进度列，额外读取 `quest_notify` 做保持不变核对；没有完成标记、紧急任务或通知写权限。新增/升级授权见 `quest_repair_sql`，旧实例可通过升级脚本安装，不必重复初始化。
- 原生依据：同一程序的 `UserQuest::set_quest` 把20组编号/进度加载到活动槽，无效非零任务的回退是编号与进度同时归0；SQL保存路径使用同名40列。本次是明确的单槽存档清理，不声称执行了全部原生放弃副作用。

API：`GET /quest-repairs/characters/{charac_no}` 读可选槽/引用/权限/维护状态；`POST /quest-repairs/preview`；`POST /quest-repairs/operations/{id}/confirm`；`GET /quest-repairs/operations/{id}`；历史列表和取消预览同组。以上均位于 `/dnf-gm/api/v1` 下，登录/CSRF/Origin/重新认证/限速沿用现有保护。

## 最小验证

本批仅4项隔离MySQL5.7检查（3项新增搜索/事务/回滚、1项原只读回归）、3项任务相关界面检查以及前端构建。生产只读搜索/状态/历史/页面检查，并通过网页策略接口启用新增能力；不执行任务清理，不打开维护，不让玩家或客户端配合。不把数据库提交或按钮可用标成游戏内效果验证。部署证据见实施台账。
