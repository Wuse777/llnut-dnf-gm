状态：**2026-11-05 本地开发版已接入存档事务/API/网页，尚未部署或完成真实镜像/游戏效果验证。**

第十二批提供槽位编解码和维护窗口基础；第十三批接入009管理库迁移、不可变快照、固定容器的预览/确认/历史/取消接口及角色详情中的装备维护页。存档UPDATE授权仍为单独显式选项，应用写入默认关闭。不得把本地合成测试结果当作客户端效果或生产维护方案已验收。

## 为什么不只判断离线

数据库登录标记或原生monitor离线响应，不证明游戏缓存已落盘，也不能阻止随后登录/加载。直接写背包可能被游戏的后续存档覆盖。因此拟采用人工安排的明确维护窗口：保留MySQL，停止全部游戏/登录写入组件并禁止其自动拉起，再允许装备事务。

**本工具绝不执行停服、启动、重启或游戏库SQL写入。** 关闭窗口现须连接固定管理库，以行锁核对中断的执行意向；只能更新管理状态和写审计，不修改游戏存档。 它不能暂停mihomo、cliproxyapi、共享Docker或dnf宿主单元。操作员必须另行安排窗口；不能执行`systemctl stop dnf`来获取窗口，因为可能连MySQL一起移除。

## 2026-11-05 实机适配修订：网页维护前置

第二十四批进行了只读生产检查：现有容器含60个s6监督服务（28个日志服务、MySQL、s6基础组件及游戏/可选组件），不是示例中原来的6个。旧探测把所有非MySQL服务都当作必须停止的写入者，无法用于真实容器。现在使用完整服务清单，并显式区分：

- `resident_components`：MySQL、已审查的日志服务和三个固定s6基础服务，维护中保留运行；存活PID必须属于对应的精确进程规则。
- 其他游戏写入组件：必须停止、禁止自动拉起，且finish完成。不会因为名字含`game`以外的前缀就遗漏。
- `dormant_components`：仅固定可选服务/未启用模板，可处理初始未启动的ready标记；仍要求停止且禁止自动启动，整个容器的进程规则继续拒绝未知finish或写入进程。不能把正在运行的游戏组件加入这一类来绕过检查。

完整清单仍必须与实际枚举完全一致。正常健康监控可以只检查核心组件，但维护清单必须包含它们。进程规则/扫描预算有界扩大至256条，按同一可执行文件inode复用哈希，避免每个supervisor重复读取相同二进制。示例不是可直接安装的生产授权：精确程序/PVF/镜像和进程规则仍由部署者根据实机安装，不从网页接收任意进程匹配条件。

### 不使用默认强制停服

实机`game_siroco11/down-signal`为SIGKILL，故不能使用普通`s6-svc -D`将它包装成安全维护。对当前程序的有限静态检查发现：SIGUSR2分支设置暂停接入、执行玩家断连，并通过shutdown-manager进入数据库队列与线程退出流程。运行中程序指纹与该样本一致，SigCgt中注册了SIGUSR2。**这些仍不是实际停服/落盘成功证据。**

新增`deploy/game_drain.py`作为后续root维护执行器的固定底层适配：

1. 只对已适配程序指纹建立计划，绑定容器/启动ID/PVF/策略/游戏PID和启动时间。
2. 执行前要求重新核对原计划，调用者必须在每一步动作前持久记录意向。
3. 使用`-O`与固定down标记禁止游戏自动拉起，再发送固定SIGUSR2；不允许网页传信号、服务名或命令。
4. 只等待退出/finish，核对正常退出状态。180秒超时不强杀、不自动重发，也不自动重新打开游戏。
5. 结果只能是“游戏退出阶段完成”，绝不是维护许可；其他写入组件尚需停止，之后仍必须通过完整进程证明和`WindowManager.issue`。

该模块没有HTTP或CLI执行入口，本批未发送任何真实信号、未停止任何服务。网页申请/状态/恢复、持久队列、独立root执行器及过渡期监控仍待下一步接入；不能声称管理员已能在网页完成整个维护流程。原有窗口工具保持下述职责。

## 1. 存档编码契约

`src/dnfgm/inventory_codec.py`：

- 存档是4字节LE解压长度与单一完整zlib流；严格限制压缩长度、解压长度及61字节对齐，拒绝截断、拼接和尾随数据。损坏不能当空背包。
- 修改选定槽位中的已知字段，保留其他槽位及未知字节。强化低5位可变，重封装高3位保留。
- 支持的底层字段：强化、锻造、耐久、增幅类型/值、附魔ID、装备原始品级、堆叠数量。此处只验证编码，不保证每个字段取值都有合法的PVF/客户端语义；生产服务层必须继续适配。
- **原始品级是普通装备类型1中的大端32位字段，不是0–100%的百分比，也不直接等于“最上级”。** 不提供虚假的百分比转换。
- 数量保持1–2,147,483,647，不恢复PVF堆叠上限，不将未知上限限制为1。
- 回收仅清零所选槽位；锁定物品拒绝直接回收，防止孤立锁记录。宠物等关联记录、未知槽位类型不走普通槽位删除；特殊类型仍需专门适配，不宣称全类型完成。
- 不允许通过该模块改变item_id、锁指针、关联记录ID或任意原始偏移。

`identity()`绑定账号、角色、容器、槽位、**整个压缩存档**、目标槽位以及镜像/PVF/游戏程序指纹。它是HMAC乐观引用，不是已发现了游戏全局物品UUID。其他槽位变化也会使旧引用失效。

`restore()`只在整个当前容器仍等于原操作的after-image时，返回原before-image；否则拒绝覆盖后续进度。事务层同时核对角色、账号、容器、槽位、原快照哈希及版本，恢复本身也是新的预览/确认操作，不覆盖旧审计。

## 2. 维护窗口生命周期

固定目录`/run/dnf-gm/maintenance`：

- `fence.lock`：root创建一次，不替换；应用只能只读打开并取得共享flock。
- `permit.json`：root签发，随机窗口ID，期限30–3600秒；绑定启动ID、容器ID/启动时间、镜像/PVF/程序/进程策略指纹和完整组件列表。
- `evidence.json`：root重新采集，最长30秒有效；失败会写入无效证据。

根工具`deploy/inventory_window.py`只允许本机root运行，命令如下。**以下是尚待生产验证的工具接口，不是要求现在执行维护：**

```bash
# 安装产物中源码包已能导入dnfgm；本地开发可使用PYTHONPATH=src。
/opt/dnf-gm/venv/bin/python /opt/dnf-gm/current/deploy/inventory_window.py init
/opt/dnf-gm/venv/bin/python /opt/dnf-gm/current/deploy/inventory_window.py issue \
  --reason '已预约的装备维护' --ttl 600 --acknowledge-writers-stopped
/opt/dnf-gm/venv/bin/python /opt/dnf-gm/current/deploy/inventory_window.py status
/opt/dnf-gm/venv/bin/python /opt/dnf-gm/current/deploy/inventory_window.py refresh
/opt/dnf-gm/venv/bin/python /opt/dnf-gm/current/deploy/inventory_window.py close --id <签发的窗口ID>
```

`issue`要求两次稳定探测，中间至少等待2秒；必须有明确操作员声明，但声明本身不能替代探测。未关闭的过期窗口也不能被新窗口静默替换。

`close`取得独占锁后使证据失效、删除许可并同步目录；存在装备事务时返回busy，不会在事务途中撤销。**只有close明确成功后，操作员才能按原维护流程恢复游戏。** 撤销许可不依赖Docker/游戏探针；但**授权恢复游戏必须成功连接原管理库完成核对**。数据库不可达、行锁超时或审计不一致时，关闭记录保持 `safe_to_resume:false`，不能启动游戏。

签发响应丢失时先查看状态，不重复签发；程序中断或证据过期会拒绝新事务。有效期与新鲜度同时核对墙上时间和绑定本次启动的单调时钟，系统时间回拨不能延长许可或复活旧证据。close响应丢失可使用原ID重试；若已存在完成核对的关闭收据，返回already_closed；许可已撤销但核对未完成时，重试原ID会继续核对，不启动任何服务。缺少关闭收据不能推断成功。`status` 区分有效窗口、已撤销但待核对（`reconciliation_required`）及已完成关闭（`closed`），仅查看不会触发SQL或恢复服务。

应用持锁次序（实际实现见 `inventory_operations.py`）：

```python
with fence.hold() as lease, database.connect() as connection:
    # 验证预览，持久提交执行意向及幂等键，不写游戏。
    # 新事务：锁定操作行，再次验证，修改游戏存档 + 快照 + 成功审计。
    lease.check()  # 必须紧邻commit，重新校验窗口/锁/证据/有效期
    connection.commit()
    # 数据库连接先关闭，再释放共享文件锁。
```

仅释放文件锁并不能证明MySQL已完成断线时的COMMIT。关闭窗口持独占文件锁，先撤销许可，再对本窗口的 `executing` 操作执行 `SELECT ... FOR UPDATE`。锁等待成功后：已提交操作保持不变；仍处于意向阶段且没有成功快照/审计的操作记为 `aborted`，不重放游戏写入。失败或超过核对预算则不授权恢复。

维护期间不得改变 `/etc/dnf-gm/config.json` 中的数据库目标、切换管理库、替换部署配置或通过其他工具写游戏库。关闭工具必须连接创建意向的同一管理库；root配置和维护者流程属于信任边界。主机重启或 `/run` 丢失不是成功关闭：先保持游戏停止、人工核对数据库意向与原维护记录，不能把缺失许可视作可恢复游戏的证明。


窗口协议不是对抗root的安全沙箱。root绕过close直接拉起游戏、外部维护工具写库、其他未声明的外部写入者，不受共享锁保护。部署前必须确认全部实际写入来源并遵守维护流程；有限次进程快照不是形式化的“未来永远没有写入”证明。

## 3. 固定只读探测

`deploy/inventory_probe.py`不会接受网页参数或任意命令。它只运行固定的Docker inspect、Docker内s6状态查询、受保护单元的systemctl is-active，并读取宿主/proc及已配置文件。

- 枚举完整`/run/service`，必须与配置完全一致，未知/新增组件拒绝。
- 除MySQL外，要求s6 `up,wantedup,normallyup,ready,pid`为`false false false true -1`；仅“down”不够。MySQL要求运行、允许正常保持运行，不能误要求它一定实现ready通知。
- 容器必须运行且无OOM、暂停、重启；两次检查的容器和组件状态一致。
- 检查Docker、dnf宿主单元、mihomo、cliproxyapi的`systemctl is-active`，不通过停核心服务绕过检查；实际单元名必须核实。这只是单元状态，不是完整业务健康证明；监控适配同时保留已配置的auxiliary检查，真实核心接口仍需生产验证。
- 以宿主cgroup扫描容器进程，含子cgroup；拒绝嵌套PID命名空间、未知进程、僵尸、异常父子链和PID/参数变化。按人工审核的可执行文件哈希、完整argv、UID、父规则进行精确匹配；不只查`df_`名称，也不自动学习白名单。
- MySQL进程必须存在且与s6的mysql服务进程具有已核对的父子关系。
- 每次采集限20秒、每条命令限5秒、输出限64KiB；进程数和文件读取有界，哈希缓存绑定inode/size/mtime/ctime，失败不返回旧的安全状态。
- 可用内存至少256MiB、Swap剩余至少1536MiB；监控器原有磁盘/资源保护仍然保留。

配置为root-owned且不可组/全局写的`/etc/dnf-gm/inventory-maintenance.json`。`deploy/inventory-maintenance.example.json`故意留空指纹和进程规则，因此不能直接启用。必须在隔离镜像中取得真实执行链和完整服务列表，逐条人工审核后填入，不将游戏二进制、玩家数据、含私密参数的配置放进公开仓库。

进程规则包含`id,role,exe,sha256,argv,uid,parents`；角色仅init/supervisor/logger/mysql，init与mysql各一个规则。该配置是维护者的信任声明，不能靠把未知进程改叫logger来证明安全。

s6字段语义依据官方文档：https://skarnet.org/software/s6/s6-svstat.html 。当前部署镜像是否支持对应版本和输出格式，还没有生产验证；格式不兼容时拒绝窗口，不能降低到简单down检查。

## 4. 与现有监控的关系

`monitor.json`增加`inventory_maintenance_enabled:false`，默认完全不加载新流程；本批没有修改生产配置。

显式开启且存在窗口时，监控器刷新并验证证据。配置必须与普通监控的容器、PVF、组件及核心单元一致，不能漏掉已有受保护单元。验证成功仅允许**保留GM进程运行**，对外`core_ok`仍为false、状态为maintenance；既有充值、邮件、奖励和原生控制不得把维护许可当游戏正常。

验证失败、过期、资源/代理失败仍按原保护规则处理GM；不因维护模式自动恢复GM。窗口结束后须人工恢复游戏并确认正常健康。配额仍是现有192MiB/25% slice，不新增独立常驻进程、Web停服权或Docker socket权限。

## 5. 数据库与网页接入

- `009-inventory-operations.sql` 增加窗口/目标索引及不可变before/after快照，全部InnoDB。快照仅授予运行用户SELECT/INSERT，不能UPDATE/DELETE；浏览器不返回完整blob或会话密钥。
- 修改容器只有背包、穿戴、角色仓库、账号仓库四种固定映射。应用默认安装不授予存档UPDATE；`upgrade-inventory.py --enable-storage-writes --acknowledge-maintenance-protocol` 是单独的维护选择，不能代替窗口验证或激活配置。
- 写表和角色归属锁定表须满足InnoDB基线，不自动改游戏表引擎。账号表只查询指定列，可以是镜像原有MyISAM；不宣称账号查询有行级事务锁。
- API 前缀 `/dnf-gm/api/v1/inventory`：`characters/{role}/{container}/{slot}`、`preview`、`operations`、`operations/{id}`、`operations/{id}/confirm`、`operations/{id}/cancel-preview`。通用操作确认接口拒绝装备操作，不能绕过维护锁。
- 角色详情列表/格子提供“维护此物品”。显示具体账号/角色/容器/槽位、变更前后和操作原因；原因和数值错误就近提示，写操作要求近期密码认证。
- 网页仅保存操作编号，重载只GET原结果，不恢复确认按钮。执行意向未核对前不创建替代预览；数据库提交后提示角色页面仍是旧快照，需要主动刷新。
- 历史恢复只取原操作的服务端快照，不接受浏览器提交的blob。原始品级按原始整数显示，不包装成百分比。
- 点券/邮件等原有操作仍使用原健康门槛，不能借装备维护许可在游戏停止时执行。
