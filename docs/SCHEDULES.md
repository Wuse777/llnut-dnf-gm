## 网页使用

1. 打开“定时运营”，选择奖励或公告，填写名称、首次时间和执行周期。**输入与显示始终是北京时间（Asia/Shanghai，UTC+8）**，即使浏览器位于其他时区；数据库保存Unix秒。
2. 支持一次性、每日、每周；周期计划可选结束时间，结束时间包含恰好到点的最后一期。修改已确认定义采用“复制为新计划草稿 → 新预览 → 激活”，不偷偷修改正在运行的奖励或时间。
3. 奖励复用批量奖励编辑器：角色名单／文件导入、筛选、在线账号、全服；账号货币、道具、金币、指定版本礼包；每账号一份或每角色一份。**预览人数只是当前估算，不是执行名单。**公告复用原生全服公告能力，不是私信。
4. 五分钟内确认预览；周期计划、全服范围、同账号逐角色重复货币分别确认。预览、激活和控制需要近期密码认证及CSRF/Origin校验。自动执行使用计划专用内部身份，不伪装仍存在的浏览器登录，也不存管理员密码。
5. 查看每期的计划时刻、实际触发开始时间、结果和原奖励任务／公告编号。奖励“已提交”不是玩家已领取，公告“已发送”不是游戏已显示。
6. 暂停／取消仅影响尚未触发期次。已经创建的奖励子任务需要在“批量奖励”中单独暂停、取消或处理失败目标；已提交的奖励不撤回。一次性失败期次不支持原计划再次执行。
7. 激活响应丢失时只查询原计划，不另建替代计划。刷新网页只恢复原ID和只读查询，不自动激活；旧预览仍可取消。可见页面每30秒读状态，后台标签页停止轮询。

## 到期与中断语义

- 每次扫描至多处理一个到期计划，并核对一个已创建子任务。扫描最短间隔5秒，与逐目标奖励共用**一个后台线程**，不是另开线程池或引入Redis/cron。奖励自身执行间隔仍由 `batch_worker_interval` 控制，扫描故障不阻塞既有奖励任务执行。
- 到期实际触发时分块读取收件规则并冻结名单，账号货币按原有规则去重；不宣称在服务离线期间已经确定了名单，也不宣称在线账号下所有角色同时在线。
- 晚于计划时间不超过300秒允许触发；超过300秒的期次记录“跳过”，不会追发。长时间离线用一个范围记录聚合错过期次数，不循环补建成千上万份任务。恢复后仍在容许时间内的当前期次可正常触发。
- 动态筛选／在线／全服没有符合角色时，跳过这一期，后续周期继续。指定名单丢失、目标限制不满足、版本变化、资源保护或结构不符属于异常，暂停未来执行等待处理。
- 上一期奖励仍在运行、暂停或需处理时不叠加下一期；处理原子任务完成或明确取消后，再恢复后续计划。手动恢复异常计划须确认已核对异常，不会补发过去期次。
- 每一期有唯一 `(schedule_id,due_at)` 约束。期次、实际名单、奖励子任务的授权及审计在**同一MySQL事务**创建。提交响应丢失后不会建立第二个期次；既有奖励执行器核对原任务并逐目标处理。
- 物品索引／策略、PVF、镜像及礼包版本在预览、激活、到期和奖励执行过程中核对。冻结名单后再次比较最终奖励快照，避免独立SQLite索引在两个读取间变化导致计划奖励被替换。
- 公告期次和原生预览在同一事务落库，**事务明确提交且释放连接后**才调用原生确认。使用原有“占位提交后单次发送”逻辑。准备事务提交不确定时，本轮不发送。
- 已准备但没有最终状态的公告经过60秒恢复宽限后，仅核对原操作；尚未取得发送占位的预览在同一操作行锁下取消，已经占位的不会重发。与仍在执行的原发送方竞争时，以该行锁和发送占位为准。任何不确定传输都记录需处理；没有业务ACK，始终不声称客户端效果。
- 定时计划取消与公告结果同时到达时，保存期次结果但不重新启用已经取消或暂停的计划。

## 接口

前缀 `/dnf-gm/api/v1`：

| 路由 | 用途 |
|---|---|
| `GET /schedules?page=1` | 每页50条计划摘要，不展开全部奖励JSON |
| `POST /schedules/preview` | 预览不可变定义和估算人数，不创建立即执行的奖励任务 |
| `GET /schedules/{id}` | 原编号查询；不返回内部身份或幂等键 |
| `POST /schedules/{id}/activate` | 会话绑定预览、指纹、幂等键和明确确认 |
| `POST /schedules/{id}/control` | pause / resume / cancel；异常恢复另需明确确认 |
| `GET /schedules/{id}/runs?page=1` | 每页50条执行记录，含原子任务编号 |

计划状态：`preview / active / paused / cancelled / completed / needs_attention`。
期次状态：`awaiting / running / finished / sent / skipped / needs_attention`。其中 `sent` 只指原生传输层结果。

## 安装、授权与回滚

- 当前合并开发版要求001至008管理迁移全部存在，健康检查不再只看最大版本号；不能用008存在掩盖漏装007。
- 008仅新增管理库的 `schedules`、`schedule_runs` InnoDB表及索引。运行账号只增加这两表的SELECT/INSERT/UPDATE权限，无DELETE、游戏表结构修改或新增游戏写权限。
- 已有实例先按部署说明完成前置迁移，再以维护权限执行 `deploy/upgrade-schedules.py`，参数来自实际实例。脚本幂等、不启动任务、不发送公告、不重启任何服务。不能重新执行bootstrap替代升级。
- `schedule_worker_enabled` 默认 `false`。显式设为 `true` 才允许激活／执行。奖励还需已有 `batch_worker_enabled` 和 `batch-reward`、reward及相关币种／邮件权限；公告还需原生monitor指纹、native-notice动作和显式审批。测试UID限制仍覆盖实际名单，测试限制生效时禁止全服公告。
- 不新增systemd服务或修改192 MiB／单核25%的共享预算、3连接上限。不改变mihomo、cliproxyapi、Docker权限或生命周期。
- 升级、回滚前先暂停未来计划，并核对已启动子任务，然后仅停止GM。保留008表、审计、期次和所有防重记录。回滚到不识别新配置键的版本时恢复兼容的私有配置或移除该键，不删除数据库记录。
- 恢复新版后先查看历史和未完成子任务，再人工启用执行器及继续计划；不会把历史期次重置成未执行。已提交奖励和已发送公告不随应用回滚撤销。

## 验证范围

本地MySQL 5.7测试覆盖到期名单、账号去重、错过聚合、边界时间、空动态范围、暂停取消、并发、配置／资源／版本变化、原子子任务、提交响应丢失、审计失败、恢复不重放和实际最小权限。前端及真实Chrome合成接口测试覆盖北京时间转换、字段提示、确认、刷新不重发、暂停、复制、手机布局。

这些测试不是生产性能、原生游戏公告显示、玩家领取或游戏缓存一致性的证明。发布部署、资源测量、实际实例迁移回滚及完整目标中的其他模块仍待完成。

## 账号名单收件范围（第二十一批，本地未部署）

定时奖励可指定账号UID或导入账号名；预览时将名称解析并绑定UID，触发时才选择这些UID下的未删除角色。账号改名不将奖励转给同名新账号；名单不完整时需要处理，不静默部分发放。复制计划保留UID规则。输入、去重、回滚兼容性见[账号名单奖励](ACCOUNT-LIST-REWARDS.md)。
