# 网页维护中心

日期：2026-11-05。**开发版，本地已接通申请／审计／计划／核对；未部署。普通写入冻结原语与应用入口已在第二十七批本地接入；完整停服、维护窗口签发及恢复执行器尚未接通。** 这不是最终仅交付“只读计划”的范围缩减，后续仍须完成可从网页执行和恢复的完整流程。

## 权限和执行能力分开

“功能与版本”新增固定的“网页维护申请”开关，现为17个开关。初次安装初始化全部已实现开关；已有网页设置不被重复安装覆盖。管理员可以从网页开启或关闭，不需要SSH改权限。关闭新维护申请后，历史查询、取消未确认计划、只读实际状态核对仍可用。

权限开启不意味着未开发的执行器已经存在。当前 `PreparationWorker` 仅调用持久协调器的只读计划、取消与状态核对；始终报告 `execute_supported=false`。网页不显示可执行的停服确认，也不会把游戏排空底层接口冒充完整停服／恢复。

## 已实现的网页流程

1. 输入维护原因，缺失提示在输入框旁。浏览器在POST前保存32位申请编号，保存失败则不提交。
2. 请求和准备审计在同一MySQL连接／事务中提交，再写固定出站包。出站写失败不丢数据库请求，保留编号供明确补投递。
3. root计划工作器读取有限大小的固定包，生成绑定原始服务状态、镜像、PVF、程序指纹及五分钟期限的计划；不接受命令、路径、服务名或信号参数。
4. 网页查询原申请、完整维护阶段与历史。只有未来完整执行器已接通、计划未过期、当前会话及运行条件符合时，才可显示“核对并确认维护”。确认要求明确勾选玩家断线影响、最近密码认证、Origin、CSRF与幂等编号。
5. 确认状态与审计同事务入队，提交结果不明只查询原编号，不自动补交或生成新请求。刷新恢复的浏览器仅查询，不自动恢复确认按钮。
6. “核对实际状态（只读）”明确请求新的root状态快照，展示采集时间以及原始运行／禁止重启／标记缺失／正常或异常退出／变化状态；后台GET轮询本身不触发探测、命令或恢复。
7. 取消只针对尚未确认的计划。取消先到达时留永久取消回执，稍后到达的准备包不能重新打开它。已确认或已开始的维护不能用取消计划代替恢复服务。

## API

全部位于 `/dnf-gm/api/v1`，必须登录。POST校验Origin与CSRF，准备、确认、取消、补投递还要求最近密码认证。状态核对为只读探测，不要求新的维护写权限。

| 路径 | 方法 | 作用 |
|---|---|---|
| `/maintenance` | GET | 开关、执行器鲜活度和完整执行能力 |
| `/maintenance/requests` | GET | 以时间与编号复合游标分页 |
| `/maintenance/requests` | POST | 固定编号及原因申请计划 |
| `/maintenance/requests/{id}` | GET | 原申请及root回执，不自动补投递 |
| `/maintenance/requests/{id}/confirm` | POST | 原计划指纹、确认编号、断线确认 |
| `/maintenance/requests/{id}/cancel` | POST | 取消尚未确认计划 |
| `/maintenance/requests/{id}/dispatch` | POST | 补投递已持久保存的原阶段／原参数 |
| `/maintenance/requests/{id}/observe` | POST | 请求只读实际状态核对 |

通用 `/operations/{id}/confirm` 拒绝维护操作；通用结果查询可关联维护中心，不会误调用普通游戏写接口。

## 状态和故障语义

- **入队**不是已经执行；旧prepared回执不能把queued覆盖成“尚未确认”。
- **游戏退出阶段完成**不是完整维护窗口，也不是存档验收完成。
- root心跳超过45秒或版本不匹配显示不可用。旧running回执不代表执行器当前仍存活。
- 回执绑定申请摘要；文件归属、不安全链接、摘要或版本不正确时拒绝，不把文件异常变成成功。
- root另存只读请求绑定与取消墓碑（目录0700、文件0600）；公开回执丢失不能用相同编号换原因、时间或版本，取消墓碑丢失公开副本也不重开。
- root公开回执丢失时先核对私有持久记录，不能把已经执行的申请标为“干净拒绝”或“尚未执行就过期”。active指针还在而私有记录缺失时保持未知，不制造取消／过期／拒绝证明。
- 完整执行器尚未接通时，即使有人伪造confirm出站包，也不会触发现有game-only排空方法。
- 刷新、重开页面、状态轮询均不自动重发确认。错误展示在当前申请结果附近，勾选提示紧邻确认控件。

## 部署与回滚边界

本批复用已有管理库 `operations` 和 `audit`，不新增迁移或游戏表权限。`maintenance_dir` 是安装者配置的固定绝对路径，不由网页提交。正式安装必须正确分离应用可写inbox与root只写results/status，完成完整执行器和监控联动后再发布；当前没有root服务安装入口，不能照着模块文件名启动生产服务。

新增发行能力 `maintenance_requests:1`。回滚目标不支持它且数据库中存在维护操作或维护开关策略时拒绝回滚，保留原请求、权限与审计；不可删除记录或伪造能力标记绕过。

当前仍未完成：普通写入冻结、固定root调度、其余游戏写入者退出、完整permit签发、关窗对账、原始状态恢复、真实配置和生产部署。不得在这之前声称线上可点击完成装备维护。全过程不停止或重启mihomo、cliproxyapi、共享Docker。

## 第二十七批：普通写入状态

状态接口新增`write_gate`，显示安装、冻结与不可核验状态；完整维护确认必须有已安装且开放的写入屏障。新游戏写入按[写入冻结协议](WRITE-ADMISSION.md)持有共享租约，维护期间保留查询与原结果恢复。当前仍未安装完整执行器，不提供无证据的网页强制解冻，后续从原维护申请完成关窗/核对/服务恢复后自动解冻，不要求日常SSH改权限。
