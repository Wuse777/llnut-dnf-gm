# 游戏库一致性备份设计（2026-11-06，只读核对）

这是设计与适配证据，不是已上线的全服备份功能。当前网页自动备份仍只覆盖GM管理库；不会因为定时任务擅自停止游戏。本批未取得数据锁、未导出游戏行、未停止任何游戏组件。

## 当前实例证据

2026-11-06只读读取information_schema和必要服务器变量：MySQL5.7.44-log；GM管理库以外18个业务库共620表，其中432张InnoDB、188张MyISAM；表及索引估计约102MiB，不含日志、PVF或程序。启用binlog，核对当时没有启用的数据库事件。这是时间点观察，不保证未来没有外部写入者。

因此不能简单照搬现有管理库的一致性事务导出，也不能把`mysqldump --single-transaction`标成所有游戏表一致。MySQL5.7.44官方工具源码明确该选项只保证多版本存储引擎的一致性，不能保证其他引擎；它也不隔离并发DDL。参考官方`mysql/mysql-server`标签`mysql-5.7.44`的`client/mysqldump.c`第518–527行。

## 两条工作流，不能混淆

1. **日常自动在线管理库备份**：保留已上线的04:00／保留7天方案，始终标明不包含游戏存档。
2. **游戏库一致性恢复点**：后续接入管理员显式维护窗口；不得自动开启窗口，不得停止会移除运行容器的dnf.service；MySQL保留，mihomo／cliproxyapi／Docker／Nginx不重启。

后者拟在已确认全部业务写入者排空后，由固定受限维护执行器完成备份，不把SQL、连接地址、命令行或root凭据交给网页。最终范围由安装时固化的完整业务库清单决定；不能只导出当前应用有列权限的几张表就称为全服备份。

## 一致性协议的实现要求

- 预检镜像／PVF／DB身份、完整库表及引擎清单、正在执行的奖励／维护、剩余空间与恢复点归属。冻结普通GM写入和奖励认领，并与管理库备份调度互斥。
- 管理员主动进入维护后，复用现有全写入组件退出与原状态恢复协议。只依赖“当前没有在线玩家”或只退出game进程不足以证明无写入者。
- 混合引擎的强一致方案需要受控锁定与一致性边界；拟使用有界的实例只读锁持有者和流式导出。锁获取超时立即退出，不杀玩家查询、不无限等待。锁释放、异常清理必须独立于导出进程成功与否。
- **先在隔离MySQL5.7演练再实现生产执行**：必须核实维护心跳／许可续期、任务调度与关窗恢复是否会依赖被锁数据库，防止备份锁导致自身恢复死锁。该点未验证前不安装自动锁库任务。
- 导出在锁边界内记录binlog坐标、库表及引擎清单，结束核对DDL未变。按固定预算流式写入，不在服务器内存聚合整库；超过预算留下失败收据，不假装完整备份。
- 文件先私有临时写入，完成校验后原子标记成功；复制时保留校验值。加密异地副本须显式配置密钥／目的地并取得真实成功回执，未配置时如实显示，不能把同磁盘目录当异地副本。

## 恢复与发布门槛

完整性清单包含源码／镜像／PVF指纹、MySQL版本、库表／引擎、导出校验值及binlog坐标。恢复在隔离的同版本MySQL上进行，核对结构、行数和必要业务关系；验证后再安排真实恢复窗口。启用binlog不等于已经具备可用的时间点恢复，仍须核实日志保留、连续归档及恢复演练。

网页最终应展示覆盖范围、备份／复制／恢复验证三个独立状态，不提供在线整库覆盖按钮；不得通过整库恢复纠正单笔点券或已领取物品。实现需新增固定受限执行能力，但日常启用与操作仍由唯一管理员在网页完成，不能要求每次SSH开权限。
